## 1. 設計

### 1-1. プロジェクトテンプレートを確認しないまま開始した

`Assets/Settings/` に `PC_RPAsset` / `Mobile_RPAsset` / `PC_Renderer` / `Mobile_Renderer` が揃っている。
これは **URP 3D テンプレート**である（2D テンプレートなら `Renderer2D` が 1 枚できる）。
初日のコミット `2DCanvasに変更` が、その手直しの跡である。

**直接の実害は小さい。** 画面はすべて uGUI の Screen Space Overlay で組んでおり、
そこはレンダーパイプラインを通らない。

実際に払った代償は 1 つに絞れる。[`FocusLightingView`](../../Assets/Scripts/Core/UI/FocusLightingView.cs) が、
ミニゲーム中の「背後を落として窓のまわりを光らせる」演出を、`Image` の暗幕と
`Fill Center` を切った枠で擬似再現している。2D テンプレートなら `Light2D` で済んだ。
コミット `スクリーンを擬似的に発光` の「擬似的に」がそれである。

**反省の言い方**: 「3D で作ってしまった」ではなく、
**「テンプレートが何を前提にしているか誰も確認しないまま、既定値がそのまま仕様になった」**。

### 1-2. 構造が必要機能に比べて重い

08-04 に[実行時 UI 生成を全廃](../Decisions/2026-08-04-remove-runtime-ui-construction.md)して
一度作り直した後でも、[`MainGameController.cs`](../../Assets/Scripts/Core/MainGameController.cs) は
**849 行 / メソッド 43 / SerializeField 12** ある。

単独で持っている仕事:

> タスク生成・出現面の抽選・レベル計算・HP・コンボ・ラッシュイベント・ポーズ・
> ミニゲームの生死・HUD 更新・バックログ更新・ダメージシェイク・結果エフェクト・セッション終了

**触る理由が 13 個あるファイルは 13 回変更される。** `Game.unity` 47 回、
`MainGameController.cs` 32 回という変更回数は、この構造の直接の帰結である。

「Raycast Target は必ず切ること。切り忘れるとポーズボタンが押せなくなる」と

**なお、デザイン PNG が 1920×1080 のレイヤー書き出しだった件とは相性が良かった。**

### 1-5. まとめ — 1-1・1-3・1-4 は同じ 1 つの失敗である

どれも「決める」のは 10 分の作業で、「各所で辻褄を合わせる」のは何十箇所の作業である。

そして 1-2 の「重すぎる」は結果である。決めなかったから各所が自前で持ち、
自前で持ったから 9,762 行になった。

## 2. 資料運用

### 2-1. 古い資料の Archive 移行が遅れた

人間なら日付を見て飛ばせるが、**AI は `Docs/` を grep して全部拾い、
古い記述と新しい記述を同じ重みで扱う。** 実際に起きた証拠が 2 つある。

**(a) 手書きの誘導板が必要になった** — [`post-merge-worklist.md`](../Plans/2026-08-06-post-merge-worklist.md) 冒頭:

> → この一覧の残りは統合作業計画に統合しました。着手の判断はそちらを見てください。
> この文書は各項目の調査結果を残すために置いてあります。

「アーカイブしたいが、調査結果は捨てたくない」状態である。`Archive/` があれば書かずに済んだ。

**(b) 資料が資料の訂正表を持ち始めた** — [`minigame-overhaul-integrated.md`](../Plans/2026-08-06-minigame-overhaul-integrated.md) に
**「古い記述のうち、実測または決定で覆ったもの」**という節がある。

**資料が他の資料の間違いを打ち消すために存在し始めたら、それは限界の合図である。**
同じ理由で「素材が来るまで着手しない」（発注書 §12）と「仮素材で先に組む」（統合計画）が
同時に生きており、後者が前者を明示的に撤回しないと通じない状態だった。

### 2-2. 「ひとまとまりの機能」単位の資料が無かった

1 つのミニゲームを理解するのに読む必要のあるファイル数:

| 機能 | ファイル | またぐフォルダ |
| --- | --- | --- |
| なぞり | **22** | 5 |
| タイピング | **20** | 5 |
| 連打 | **17** | 5 |
| QTE | **15** | 4 |
| 仕分け | **14** | 4 |
| タイミング | 9 | 3 |

`Architecture` / `Specifications` / `Plans` / `Decisions` という切り方は**書く側の都合**の分類である。
読む側（人も AI も）は必ず**「連打を直したい」から入る**。

**AI にとっては、全部読めてしまうことが逆に害になる。**
人間は「08-03 の計画書か、もう古いな」と判断して読まないので、散らばりの被害を受けにくい。
**同じ資料構造でも、AI のほうが強く壊れる。**

**なお、答えは一部作ってあった。** `Docs/README.md` に
「ミニゲームの追加・改造手順 — 自分の担当分に手を入れる人はここまでで足りる」とあり、
[`mini-game-catalog.md`](../Architecture/mini-game-catalog.md) が「最初に読む 1 枚」の役をしていた。
**発明済みで、ミニゲームにしか適用しなかった**というのが正確である。
タスク吹き出し・演出・デバイス切替・チュートリアルには、この 1 枚が無かった。

### 2-3. 次回の形

```
Docs/
  Features/<機能名>/
    README.md                  ← 現役の入口。ここだけで担当作業が終わる
    仕様・決定・現在の実装
  Archive/<日付>-<名前>.md     ← 完了・撤回した Plans を即移動
```

規則は 2 つで足りる。

1. **Plans は完了時に必ず `Archive/` へ移す。** 残す価値のある調査結果は、移す前に
   機能の `README.md` へ吸い上げる。
2. **`Features/` の外を AI に読ませない。** `AGENTS.md` の「対応資料を読む」の箇所に
   `Archive/` の除外を 1 行足す。

## 3. AI 協働

### 3-1. 出力の確認 — 読んでも見つからない形の欠陥があった

最終日に見つかった進行不能バグ（[§1-1](../Plans/2026-08-06-post-merge-worklist.md)）は、
**単独では壊れていない 2 つのコードが噛み合ったときだけ詰む**形だった。

**片方** — `MainGameController.TryAssignPlayer` の握りつぶし:

```csharp
if (overrideTaskLifetimeSec > 0f && !success)
{
    Debug.Log("[Tutorial] 失敗判定を無視し、クリアまで継続します。");
    return;   // ← CompletePlayerMiniGame を呼ばずに抜ける
}
```

**もう片方** — `MiniGameBase.FinishGame` が通知より先に `IsPlaying` を落としている
（二重発火防止としては正しい書き方）。

噛み合うと、タイマーと入力が死に、通知が握りつぶされ、窓が閉じず、
タスク操作もデバイス切替も止まったままになる。**再挑戦の手段が無いので詰む。**

**最終日まで隠れていた理由**: 連打の難度 3 でしか出ない。チュートリアル中で
**最初に失敗しうるミニゲーム**がそこだからである。テストプレイでは成功してしまうので誰も踏まない。

**修正は握りつぶしを消すだけだった。** `TutorialSequenceController` は失敗時に
出題し直す処理を最初から持っており、握りつぶしが手前で効いて到達できていなかった。追加コードはゼロ。

**反省の言い方**: 「AI 出力をざっとしか見なかった」ではなく、
**「チュートリアルを失敗しながら通す経路を一度も実行しなかった」**。
読む量を増やしてもこの形は出てこない。

### 3-2. 指示書（発注書）

[`minigame-ui-assets.md`](../Specifications/minigame-ui-assets.md) — 364 行、作成 2026-08-05。

| 区分 | 発注 | 納品 | 使えたか |
| --- | --- | --- | --- |
| 共通ウィンドウフレーム | 12 | 12 | ○ |
| 仕分け | 12 | 6 | ○（残り 6 は「作らない」決定で足りた） |
| 連打 | 9 | 0 | 仮素材で自作 |
| タイミング | 6 | 0 | 仮素材で自作 |
| なぞり | 8 | 0 | 後回し |
| QTE | 3 | **4** | **×（仕様未定で 1 枚も使えず）** |
| 合計 | 50 | 22 | **実際に使えたのは 18 枚** |

**文書としては良く書けている。** 発注書として珍しく「要らないもの」を明示している
（§9「絵が要らないと確定しているもの」、§1「状態違いは要らない」、§3「24 枚は要らない。8 枚でよい」）。
そして全部に理由が付いているため、描く側は指示を暗記せずに判断できる。

**最も効いたのは指示書そのものではない。** §8 の仕組みである。

> 先に**寸法とふちだけ仕様どおりに合わせた白い仮素材**を納品先に置き、meta（9 スライスのふち・縮小率）を
> 作っておく。本素材は同名で上書きさせる。**Prefab 側の作業は発生しない。**

唯一の失敗は納品先の食い違いだけで、仕組み自体は機能した。

**効かなかった点**: 書いたのが 4 日目である。中身の問題ではなく、
**依存の向き（素材が来ないと組めない）を発見したのが遅かった**。
結果 §12 が「素材が届いてから着手する作業」という待ちのリストになり、
最終日に「仮素材で先に組む」へ方針転換して実質撤回した。
QTE は 3 枚発注に対し 4 枚届いたのに、仕様未定で 1 枚も使えず死蔵した。

**次回**: 仮素材＋同名上書きの方式は完成しているので、**初日に空の仮素材だけ置いて枠を作る。**
指示書は「何を描くか」より先に「何を置く場所があるか」を確定させる文書として使う。

### 3-3. AI が Unity を直接触る運用（Pipeline）

[`unity-pipeline.md`](../Operations/unity-pipeline.md) — 121 行。うち約 60 行が落とし穴の記録である。

**この運用の本質はサイレント失敗との戦いである。**

> どれか欠けると保存されず、**保存されなかったこと自体にも気づけない。**

```
SerializedObject → ApplyModifiedPropertiesWithoutUndo() → SetDirty()
                 → MarkSceneDirty() → SaveScene() → 開き直して確認
```

**AI が「変更しました」と報告して、実際には何も保存されていない。** エラーも出ない。
同型のものがもう 1 つあり、Prefab から作られたオブジェクトをシーン側だけ直すと
他のシーンに反映されないまま「できました」になる。

**踏んだ地雷（すべてエラーメッセージが役に立たない種類）:**

| | |
| --- | --- |
| `eval_file` はメソッド本体 | `using` も `class` も書けない。型は完全修飾 |
| `unity test` が起動を拒否 | `ProjectVersion.txt` は `6000.4.4f1`、実 Editor は `6000.3.21f1` |
| コンソールが文字化け | シェルが cp932 |
| `delete_asset` が動かない | 引数は `--path` ではなく `--asset`、加えて `--confirm true` |
| 非アクティブが拾えない | `FindObjectsInactive.Include` が要る |
| CRLF 全面差分 | `core.autocrlf=true`。スクリプトで書き換えると LF になる |

**一方、はっきり成果が出た使い方がある。** `EditorApplication.update` に登録して
`StringBuilder` へ書き溜め、`get_console_logs` で回収する計測である。

| | 直す前 | 直した後 |
| --- | --- | --- |
| 明転 | **0 秒（飛んでいた）** | **0.297 秒**（設定 0.30） |
| 蓋のコマ | 最初の数コマが飛ぶ | 各 0.20 / 0.27 / 0.20 秒 |

「フェードが飛んでいる気がする」を 0 秒だと確定させたのはこの手法である。目視では詰められない。

**総括**: Pipeline は **「AI に作らせる」より「AI に測らせる」ほうが投資対効果が高かった。**
書き込みは 4 段の儀式とサイレント失敗のリスクを毎回背負うが、読み取り・計測は失敗しても害がなく、
人間には出せない精度が出る。

### 3-4. 知らない分野について、AI に質問・確認をしなかった

**AI は周りのコードに合わせる。** これは指示しなくてもそうなる既定動作である。
既存が全部 `anchoredPosition` なら、AI は `anchoredPosition` を選ぶ。一貫性を優先するからである。

> **初日の数コミットで選んだ手法が、以後 AI によって自動的に増幅される。**

人間だけの開発なら、3 日目あたりで誰かが「毎回座標を打つのは面倒だ」と言い出す可能性がある。
**AI は言い出さない。しかも一貫性が高いほど言い出さない。**
規律を保って統一していたことが、そのまま「見直す機会が来ない」に直結した。

**AI 協働では、初期の手法選択の重みが人間だけのときより重い。**

**対処法は 1 つ。実装を頼む前に、1 回だけ選択肢を聞く。**

> 「この UI の組み方の選択肢を挙げて、それぞれの利点と欠点を出して。決めるのはこっちでやる」

知識が無くても投げられる問いで、答えを見てから選べる。
**今回、このフェーズが 1 回も無かった。** 最初から「作って」で入ったため、
AI は既定値を出し、それが仕様になった。

これは 1-1（URP テンプレート）とまったく同じ形である。

## 4. 次回に持っていくもの

### 着手前に決めて `AGENTS.md` に書く（3 行で足りる）

| | 決めること |
| --- | --- |
| 配置 | 手置き絶対座標 か Layout システムか。**混ぜると崩れるので必ずどちらか** |
| 非表示 | `SetActive` / `CanvasGroup` / `enabled` のどれか 1 つ |
| 演出の時間 | DOTween かコルーチンか。`timeScale` 0 のとき動くか |

**この 3 行があれば、1-1・1-3・1-4 の反省は全部消えていた。**

### 手順として持っていくもの

1. **プロジェクト作成時にテンプレートの前提を確認する。** 既定値を仕様にしない。
2. **実装を頼む前に、選択肢を 1 回聞く。** 知らない分野ほど効く。
3. **初日に仮素材で枠を作る。** 素材待ちの依存を作らない（§3-2 の方式は完成済み）。
4. **Plans は完了時に `Archive/` へ移す。** AI に古い記述を読ませない。
5. **機能ごとに「最初に読む 1 枚」を置く。** `mini-game-catalog.md` を全機能に広げる。
6. **AI には作らせるより測らせる。** 計測は失敗しても害が無く、精度が出る。
7. **「わざと失敗しながら通す」経路を一度は実行する。** 読むだけでは見つからない欠陥がある。
