### 1-1. チュートリアルがミニゲーム失敗で止まる

**`main` 由来。こちらのマージが原因ではない。** `main` 単独でも同じように止まる。

`MainGameController.TryAssignPlayer` に握りつぶしがある:

```csharp
if (overrideTaskLifetimeSec > 0f && !success)
{
    Debug.Log("[Tutorial] 失敗判定を無視し、クリアまで継続します。");
    return;   // ← CompletePlayerMiniGame を呼ばずに抜ける
}
```

`Tutorial.unity` は `overrideTaskLifetimeSec: 99` なので、チュートリアル中は常にこの経路。

ところが `MiniGameBase.FinishGame` は**通知より先に `IsPlaying = false` にしている**:

```csharp
protected void FinishGame(bool success, string reason = "")
{
    if (!IsPlaying) return;   // 二重発火防止ガード
    IsPlaying = false;
    ...
    OnCompleted?.Invoke(success, reason);
}
```

したがって失敗した瞬間にこうなる:

1. `IsPlaying = false` になり `Update` が素通りする → **タイマーも入力も死ぬ**
2. 通知が握りつぶされ `CompletePlayerMiniGame` に届かない
3. → `TaskResolved` が飛ばない → `CloseMiniGame` が呼ばれない → **窓が閉じない**
4. `PlayerMiniGameActiveChanged(true)` が出たままなので、タスク操作もデバイス切替も止まったまま

コメントは「クリアまで継続します」だが、**その時点でミニゲームは既に終わっている。**
再挑戦の手段が無いので詰む。連打の難度 3 で出るのは、そこがチュートリアルで
**最初に失敗しうるミニゲーム**だから（それ以前は難度 1 でたいてい成功する）。

**修正: 握りつぶしをやめる。**
`TutorialSequenceController.OnTaskResolved` は `WaitMiniGameClear` / `WaitAiProcess` などで
**失敗したら出題し直す処理を既に持っている**（316〜388 行）。
握りつぶしが先に効くせいで、そのリトライに到達できていないだけ。外せば設計どおり動く。

**決定: チュートリアル中も失敗で HP を減らす。**
ダメージの説明はチュートリアルの題材そのものなので、そのまま通す。
`GameSession` 側の damage には手を入れない。

### 1-2. シーン読み込みでフェードインが飛ぶ

難易度選択 → ゲーム画面を再生中に毎フレーム計測した結果:

| 時刻 | 不透明度 | フレーム間隔 | シーン |
| --- | --- | --- | --- |
| 0.018 〜 0.243 | 0.00 → 1.00 | 2〜5 ms | DifficultySelect |
| 0.243 〜 0.318 | 1.00 | 3 ms | DifficultySelect |
| **0.318 〜 0.675** | **フレームが飛ぶ** | **357 ms** | → Game |
| 0.675 以降 | **0.00** | 2〜3 ms | Game |

暗転は 0.25 秒かけて正常に動いている。問題は `SceneManager.LoadScene` が同期で、
**そのフレームだけ 357 ms 続く**こと。DOTween は実時間で動くため、
**待ち 0.05 + 明転 0.30 = 0.35 秒ぶんを 1 回でまとめて消化してしまう。**

**特定の遷移の問題ではない。** 行き先の読み込みが 0.35 秒を超えれば同じことが起きる。
Game が一番重いので目立っているだけ。

**修正: 明転を「読み込みが終わってから」始める。**
`PcLidView` が既にこの形（`action()` のあと `yield return null` をはさむ）なので、
`FadeOverlayView` を同じコルーチン方式に書き換える。
`LoadSceneAsync` にする手もあるが、読み込み中に何も出さないなら見た目は変わらない。

## 2. ミニゲーム中の操作を開放する

挙げてもらった「後ろの暗い部分をなくす」と「他画面を暗くする機能を廃止」は、
**見た目の面では同じ 1 つの部品**を指している。機能の話と分けて考える。

### 2-1. 見た目 — コードは触らずに済む

`FocusLightingView` が 2 枚持っている:

| 名前 | 役割 | 今の値 |
| --- | --- | --- |
| `dimmer` | 全画面の暗幕 | `dimAlpha 0.5` |
| `glow` | 窓のまわりの光（`Fill Center` を切った枠） | `glowAlpha 0.4` |

「ぼかした影っぽくしてウィンドウ感を出す」は `glow` がまさにその位置にいる層。
**`dimAlpha` を 0 にして `glow` の Sprite を影に差し替える**のが最短で、どちらも Inspector の値。

→ **影の絵が要る（素材待ち）。**

### 2-2. 機能 — AI 依頼を通す

`GameManager.OnPlayerMiniGameActiveChanged` が 3 つを同時にやっている:

1. `SetSwitchEnabled(!active)` — デバイス切替を止める
2. `focusLightingView.SetFocused(active)` — 暗くする（→ 2-1）
3. `workspace.SetInteractionEnabled(!active)` — **全面のタスク操作を殺す** ← AI 依頼を塞いでいる本体

3 を外せば右クリックの AI 依頼は通る。ただし懸念どおり**左クリックも素通りになる。**

`MainGameController.TryAssignPlayer` は `activePlayerTaskId` を見ていない。
`miniGameHostView.Spawn` は中身を捨てて入れ替えるため、
**2 つ目を開くと 1 つ目が黙って消える**（コールバックは残るので状態も壊れる）。

→ `TryAssignPlayer` の入口に `activePlayerTaskId >= 0` なら弾くガードを足す。
`ForceAiOnlyMode` のガードのすぐ下が置き場所。

**決定: 1（デバイス切替の禁止）は残す。** 外すのは 3 だけ。
ミニゲームは面をまたがないので、切替を止めておくほうが事故が少ない。
